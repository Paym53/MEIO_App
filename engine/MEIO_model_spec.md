# MEIO model (Seeker): specification of assumptions, mechanics & dynamics

The same list is in the Excel sheet *Model_Assumptions*. The implementation is `meio_seeker_stochastic.py` (v16): every rule below is written once, as Seeker Terms in its section 3. `reference_simulator.py` implements rules A–J a second time, independently, and `test_engine.py` requires both to agree in every scenario.
Status: **Confirmed** = decided by user · **Given** = user data · **Proposed** = default, to be confirmed.


## A. Time & planning

- **A01 Period** (Confirmed; User Q1; → Settings): One period = one calendar week. Period 1 starts on Settings!PlanningStartDate. All times (lead times, shelf lives) are whole periods.
- **A02 Planning horizon** (Confirmed; User Q1; → Settings): The model simulates and optimizes H = 36 periods (Settings!HorizonPeriods).
- **A03 Review period = re-planning cadence** (⚠️ Proposed; User Q1/Q29; → Settings!ReviewPeriod): The model is re-run every R = 2 weeks with the then-actual state (inventory, open orders, new forecast). Decisions falling in periods 1..R are 'commit now'; decisions in later periods are indicative and will be re-optimized at the next review. Inventory is still checked and orders can still be placed every week (s,S is weekly).
- **A04 Event sequence within a period t** (⚠️ Proposed; Proposed (changed: review before demand); → Math model §3): E1) Receipts due in t arrive with full shelf life. E2) FG review at DC → production order (D02); its raw materials leave RMW the same week (B02). E3) RM review at RMW on echelon stock → supplier orders (D01). E4) Customer demand of t is served from DC stock (H02/H03). E5) Holding cost on end-of-week on-hand. E6) Ageing −1 week; lots no longer usable are scrapped immediately (F05). Reviews happen at the START of the week (before demand), so week-1 decisions depend only on today's known stock and are exact.
- **A05 No terminal valuation** (Confirmed; User (06.11. 20:48); → Settings!TerminalInventoryValue): Inventory left at the end of the horizon has no value and no cost beyond holding. End-of-horizon effects (running stock down) are acceptable because only the first R periods are committed and the model rolls forward: FG orders placed in weeks 1–2 arrive in weeks 7–8 and are below every channel's freshness rule by week 36. No end-of-horizon rule is added; the last weeks of the plan are indicative (stress tests 06.11.: week 36 is the weakest rule on fresh scenarios).

## B. Network & material flow

- **B01 Network** (Given; User; → Locations, Items, Sourcing): Suppliers (Erdbeerhof Köln: RM3; Verpackungslieferant: RM1, RM2; Ananas CR: RM4) → raw material warehouse RMW → production site KAJA → distribution center DC → channels AMZ, D2C, B2B. One finished good FG1, four raw materials.
- **B02 RMW → KAJA transfer (derived decision)** (Confirmed; User Q5/Q8; → Lanes L_RMW_KAJA, BOM): Not optimized separately. In the week a production order of q units is placed, BOM_k × q of each raw material k is withdrawn from RMW (FEFO, F04) and shipped to KAJA. The transfer time is contained in the production lead time.
- **B03 KAJA holds no inventory** (Given; User; → Locations KAJA): Raw materials are consumed on arrival; finished goods are shipped to the DC on completion. There is no stock at KAJA in the model, only the production pipeline.
- **B04 DC → channels** (Confirmed; User Q15; → Lanes, LeadTimeDist LT_ZERO): Channels are served directly from the DC with zero transit time (instant serve).
- **B05 Storage capacity** (Confirmed; User Q22; → Locations): No storage capacity limits at RMW or DC.

## C. Inventory policy (s,S)

- **C01 FG1 policy at DC** (Confirmed; User Q2; → Settings!FGInventoryPositionBasis): Dynamic (s_t, S_t) per week t for FG1. Inventory position IP_FG(t) at the start-of-week review = DC on-hand still sellable this week (remaining shelf life ≥ 16) + all open production orders (FG pipeline). Lost sales → no backorders in IP. If IP_FG(t) < s_t (C06), a production order of S_t − IP_FG(t) is triggered and rounded/limited per D02.
- **C02 Unsellable FG is wasted immediately** (Confirmed; User (19:49); → Math model E2/E6): FG lots that no channel can use any more are scrapped immediately (waste cost) and never count in IP_FG. A lot with exactly 16 weeks left still counts at the start-of-week review and can serve this week's D2C demand; whatever is left of it at week end is scrapped.
- **C03 RM policy at RMW (echelon)** (Confirmed; User Q2/Q4; → Settings!RMInventoryPositionBasis): Dynamic (s_kt, S_kt) per raw material k and week t, in RM units. Echelon inventory position IP_k(t) = usable RMW on-hand of k + open supplier orders of k + BOM_k × IP_FG(t) (raw material embedded in downstream FG stock and production pipeline). The RM review happens after the FG review in the same week, so a production order itself does not change the echelon position. Only RM lots still usable next week count (C04). If IP_k(t) < s_kt (C06), order S_kt − IP_k(t), rounded/limited per D01.
- **C04 Unusable RM is wasted immediately** (Confirmed; User (19:49), by analogy; → Math model E3/E6): Same rule as C02 for perishable raw materials: RM3/RM4 lots that can no longer be used in production are scrapped immediately. In IP_k only lots with remaining shelf life ≥ 37 at the RM review count (still usable, ≥ 36, at next week's production). Non-perishables (RM1, RM2) count fully.
- **C05 Weekly variable s,S** (Confirmed; User Q3; → Settings!PolicyBlockLength): s and S may take a different value in every week of the horizon (block length 1). Encoding: s_t ≥ 0 and gap Δ_t = S_t − s_t ≥ 0, so that S_t ≥ s_t holds by construction.
- **C06 Strict order trigger** (Confirmed; Design; → Math model E2/E3): An order is triggered when IP < s (strictly), and the quantity is S − IP > 0 before rounding. s = 0 therefore means 'never order this week'. This avoids MOQ-inflated orders when IP = s = S.

## D. Order & production rules

- **D01 Raw material order quantity** (Confirmed; User Q20; → Sourcing): q = S − IP → round UP to OrderMultiple → if q < MOQ then q = MOQ → if q > EffectiveMaxOrderQty then q = EffectiveMaxOrderQty (MaxOrderQty rounded down to a multiple of OrderMultiple: RM1 19,440, RM2 39,600, RM3 1,000 kg, RM4 10,000 kg). At most 1 order per raw material per week; the max applies per order.
- **D02 Production order quantity** (Confirmed; User Q9; → Production, BOM): q = S − IP → round UP to BatchSize (100) → raise to MOQ (6,000) → cap at MaxQtyPerOrder (50,000) → cap by raw material availability: for each component k, q ≤ usable RMW stock of k / BOM_k → round DOWN to BatchSize. If the result is < MOQ, nothing is produced this week.
- **D03 One production line** (Confirmed; User Q7; → Production!MaxOrdersPerPeriod): At most one production order can be started per week, and orders complete in the sequence they were started (an order started later can never arrive at the DC earlier).
- **D04 Concurrent production orders** (Confirmed; User (20:00), option 1; → Production): Several production orders can be in the pipeline at the same time (one start per week, each taking the production lead time); with no overtaking (E04) they arrive in start order.
- **D05 Rounding direction** (⚠️ Proposed; Proposed; → —): Policy quantities are rounded UP to the batch multiple (to reach the order-up-to level). Availability caps are rounded DOWN (you cannot produce from material you don't have).

## E. Lead times

- **E01 Supplier lead time** (Confirmed; User Q7; → Sourcing, LeadTimeDist): Time from order placement in week t to arrival at RMW at the start of week t + L. Current data: fixed RM1 4, RM2 4, RM3 8, RM4 12 weeks.
- **E02 Production lead time** (Confirmed; User Q5/Q6; → Production, LeadTimeDist): Time from production order in week t (raw materials leave RMW the same week) to arrival at the DC at the start of week t + L. Includes the RMW→KAJA transfer, production and KAJA→DC transport. Current data: fixed 6 weeks.
- **E03 Stochastic lead times (switchable)** (Confirmed; User Q7; → LeadTimeDist): Each lead time is a discrete distribution (LeadTimeDist). The example uses fixed distributions; stochastic variants exist as *_STOCH IDs (RM1/RM2 4|6, RM3 8|12, RM4 12|16, production 6|8). Switch by changing LeadTimeDistID in Sourcing / Production. A lead time is drawn independently per order and scenario.
- **E04 No order crossing** (Confirmed; User Q21/Q7; → Settings!LeadTimeCrossing): Orders from the same source never overtake each other: arrival(order n) = max(t_n + L_n, arrival(order n−1)). Applies to each raw material's supplier stream and to the production line.

## F. Shelf life, FEFO & waste

- **F01 Shelf life starts at arrival** (Confirmed; User Q2/Q10; → Items): The shelf-life clock of a lot starts when it arrives at its stocking location: raw materials at RMW, FG1 at the DC. Time at the supplier, in transit or in production does not consume shelf life. Each lot arrives with full shelf life.
- **F02 Shelf lives** (⚠️ Proposed; User + change; → Items!ShelfLife): FG1 36 weeks from DC arrival. RM3 Erdbeere and RM4 Ananas 52 weeks from RMW arrival (raised from 44, as you allowed, to lengthen the usable window). RM1 Große Dose and RM2 Pappboden do not expire.
- **F03 Freshness rule at production** (Confirmed; User Q11; → BOM!MinRemainingShelfLife): RM3/RM4 can be withdrawn for production only if their remaining shelf life is ≥ 36 weeks in the production-order week. Usable window after arrival = 52 − 36 = 16 weeks.
- **F04 FEFO issuing** (Confirmed; User Q13; → Settings!IssuingRule): At RMW and DC, lots are issued first-expired-first-out among the lots eligible for the use (production, or a specific channel).
- **F05 Waste** (Confirmed; User Q14/Q26; → Costs!WasteCost): A lot is scrapped at the end of the week in which it becomes unusable for every purpose: RM3/RM4 when remaining shelf life < 36; FG1 when remaining shelf life < 16 (the lowest channel requirement). Waste cost = scrap cost per unit only (material value is sunk).

## G. Demand & scenarios

- **G01 Probabilistic forecast input** (Confirmed; User; → Demand): Per channel and week: 10 quantiles at probability levels 0.05, 0.15, …, 0.95 (each quantile = centre of a 10% probability band), as produced by a probabilistic forecaster.
- **G02 Scenario sampling** (⚠️ Proposed; User Q19 + proposed tails; → Settings!DemandSampling): Per scenario, channel and week: draw u ~ Uniform(0,1) and read demand from the piecewise-linear quantile function through the 10 points. Tails: from u = 0 at max(0, Q05 − (Q15 − Q05)/2) to Q05; from Q95 to Q95 + (Q95 − Q85)/2 at u = 1. Rounded to whole units. Independent across channels and weeks.
- **G03 Example forecast character** (⚠️ Proposed; Generated; → Demand!Event): Generated data: seasonal baseline with spiky week-to-week noise, promotion weeks (AMZ w9, w10, w27; D2C w14, w30; B2B w18, w33) with 2.2–3.8× mean and wide uncertainty, flat weeks (AMZ w20–22; D2C w5–7; B2B w24–25) with a stable level and very narrow uncertainty. Average about 1,400 units a week in total.
- **G04 Unmet demand** (Confirmed; User Q17, User (06.11. 20:48); → Channels!UnmetDemand): Demand not served in its week is lost (all channels). No backorders. Lost sales have no cost: they are limited only by the fill-rate rules (H05). Consequence: a plan that misses rules sells less and therefore looks cheaper, so costs are only compared between plans that meet the same rules.

## H. Channel allocation & fill rate

- **H01 Channel eligibility** (Confirmed; User Q15; → Channels!MinRemainingShelfLife): A unit can be shipped to channel c only if its remaining shelf life ≥ requirement_c: AMZ 24, D2C 16, B2B 24 weeks. FG1 is therefore sellable to AMZ/B2B for 12 weeks after DC arrival and to D2C for 20 weeks.
- **H02 Shortage allocation** (Confirmed; User Q16; → Channels!ShortagePriority): Channels are served one after another in order of fill-rate target, highest first: D2C (0.98) → B2B (0.95) → AMZ (0.90). Each channel takes as much as it can of its demand before the next is served.
- **H03 Lot selection per channel** (⚠️ Proposed; Proposed (FEFO + H01); → —): Within its turn, a channel takes FEFO from the lots eligible for it. As a result D2C consumes the older 16–23-week lots that AMZ/B2B cannot take anyway, before touching fresher stock.
- **H04 Fill-rate definition** (Confirmed; User Q18; → Settings!FillRateDefinition): FR(c,t) = units served to channel c in week t ÷ demand of c in week t; FR = 1 if demand = 0. Measured per channel, per week, per scenario.
- **H05 Fill-rate constraint (chance)** (Confirmed; User Q18; → Settings!FillRateChanceLevel): For every channel c and every constrained week t: the share of scenarios with FR(c,t) ≥ target_c must be ≥ 99%. With N = 200 scenarios at most 2 scenarios may miss per (c,t).
- **H06 Constrained weeks** (⚠️ Proposed; Proposed; → Settings!FillRateEnforcementStart): Constraints apply from the first week that any new decision can influence, i.e. week 1 + production lead time (= week 7 with fixed 6 weeks). Earlier weeks are fully determined by the initial state and open orders; they are reported but not constrained (otherwise the model could be infeasible whatever it decides).
- **H07 Chance constraint in Seeker (two equivalent forms)** (Confirmed; Design; → Math model C1; script §3): FILL_RATE_CONSTRAINT_FORM = 'frequency' (default): aggregate_relative_frequency_geq(FR, target) ≥ α. 'quantile': with v = ⌊(1 − α)·N⌋ allowed misses (α = 0.99, N = 200 → v = 2), the (v+1)-th smallest fill rate ≥ target, i.e. aggregate_quantile(FR, 1 − α, lowest) ≥ target. Both accept exactly the same plans; 'frequency' searched better in your runs (K13).

## I. Costs & objective

- **I01 Objective** (Confirmed; User Q27; → —): Minimize expected total cost over the horizon (average over scenarios) = RM ordering + production + transport + holding + waste, subject to the fill-rate chance constraints. No shortage penalty.
- **I02 Raw material ordering** (Confirmed; User Q25; → Costs): Per order: fixed cost per raw material order line + variable cost per unit ordered. Each raw material is its own order line, with no shared fixed cost per supplier delivery.
- **I03 Production** (Confirmed; User Q24; → Costs, CostTiers): Per production order: fixed cost + variable unit cost from tier table CT_FG1_PROD, all-units pricing on the order quantity (the whole order is priced at the tier its quantity falls into).
- **I04 Transport** (Confirmed; User Q24; → Lanes, CostTiers): KAJA→DC transport is priced per production order quantity with tier table CT_FG1_TRANSPORT (all-units). RMW→KAJA transfers and DC→channel shipments are free.
- **I05 Holding** (Confirmed; User Q23; → Costs!HoldingCost): Holding cost per unit per week on end-of-week on-hand at RMW (raw materials) and DC (FG1). No holding cost on pipeline or in-transit stock.
- **I06 Waste** (Confirmed; User Q26; → Costs!WasteCost): Scrap cost per unit for every scrapped lot (F05).
- **I07 Cost timing & scope** (⚠️ Proposed; User Q23/Q26 + design; → Math model §4): Ordering, production and transport costs are counted in the week the order is placed, for all orders placed in weeks 1..H (also those arriving after H). Orders already open at the start are sunk and not counted. Holding is charged on end-of-week on-hand, including lots scrapped at the end of that week. Raw material purchase cost of later-wasted material is part of ordering cost; waste adds only the scrap cost.

## J. Initial state

- **J01 On-hand at start** (Confirmed; User Q28; → Init_Inventory): Init_Inventory lists on-hand stock at the start of week 1 per location × item × remaining shelf life lot.
- **J02 Open orders** (Confirmed; User Q28; → Open_Orders): Open_Orders lists released but not yet arrived supplier orders (Purchase) and production orders (Production) with their arrival week. Open production orders already consumed their raw materials. Lots arrive with full shelf life (F01) unless RemainingShelfLifeAtArrival is given.
- **J03 Open orders in policy positions** (⚠️ Proposed; Proposed (follows C01/C03); → —): Open production orders count in IP_FG; open supplier orders count in IP_k; both count in the echelon position via C03.

## K. Optimization (Seeker)

- **K01 Decision variables** (Confirmed; Design; → meio_seeker_stochastic.py §2): Per stock point j (FG1 at DC; RM1–RM4 at RMW) and active week t: σ_jt, δ_jt ∈ {0, 1, …, upper bound} integers; s_jt = m_j·σ_jt and S_jt = s_jt + m_j·δ_jt, with decision step m_j (K11). 244 variables with the current data (K04).
- **K04 Inactive tail weeks fixed to s = S = 0** (Confirmed; Design; → meio_seeker_stochastic.py §2): With no terminal value, an order that cannot arrive within the horizon is pure cost. So FG s,S are only free for t ≤ H − min production LT (= 30), and RM k only for t ≤ H − min production LT − min LT_k (RM1/RM2 26, RM3 22, RM4 18). Later weeks are fixed to 0, which shrinks the search from 360 to 244 variables.
- **K05 Variable bounds (lower 0, upper from the forecast)** (Confirmed; User (22:55, 19:40); → meio_seeker_stochastic.py §0, §2): Lower bound 0 for every variable (s = 0 means 'do not order this week'). Upper bounds, with Q95 = sum of the weekly 95% quantile of total demand over a window of weeks (cut at the horizon): reorder point s of FG ≤ Q95 over (max production LT + 1 + EXTRA_COVER_WEEKS['FG']) weeks; reorder point s of RM k ≤ BOM_k × Q95 over (max LT_k + max production LT + 1 + EXTRA_COVER_WEEKS[k]) weeks; FG gap S − s ≤ min(max production qty; max(MOQ; Q95 over the 20 sellable weeks after arrival)); RM gap S − s ≤ max order qty (a larger gap behaves exactly like 'order the maximum'), perishable RM additionally ≤ max(MOQ; BOM × Q95 over the 16 usable weeks after arrival). Bounds are rounded up to the decision step (K11) and raised if needed to contain the start policy (K12). EXTRA_COVER_WEEKS per stock point in §0: FG 8, RM1 4, RM2 4, RM3 8, RM4 4 — RM3 raised from 4 to 8 because its week-12 reorder point sat at the bound in the 05.11. runs (week-12 bound 23,300 → 27,550 kg); FG raised from 4 to 8 because its week-13 reorder point sat at the bound in two 250 s runs (05.11., 06.11.; week-13 bound 25,300 → 35,500 cans). If a run reports a reorder point at its upper bound (console NOTE and Summary row, naming the setting), raise that stock point's EXTRA_COVER_WEEKS. Search space about 10^480.
- **K06 One model, written once in Seeker** (Confirmed; User (18:42); → meio_seeker_stochastic.py §3): Every rule of sections A–J (lots and shelf life, FEFO, channel priority, (s,S) ordering with MOQ/batch/max, echelon positions, lead times without overtaking, waste, costs, fill rates) is written exactly once: as Seeker Terms in section 3 of the script, in Seeker's stochastic environment. No other code computes supply-chain dynamics; every reported number comes from Seeker evaluating this one model (optimization §5, out-of-sample check §6). Python only reads data, sets variable bounds, computes the start-policy formula (§4) and formats the report. Retired: the sampling version meio_seeker.py (NumPy simulator inside Seeker) and the NumPy replay of v7–v9. Correctness is checked outside the script: an automated test suite compares the Seeker model scenario by scenario with an independent reference implementation (cost, cost parts, fill rates, orders, arrivals, stock, waste, holding) and is itself mutation-tested; on real Seeker 2.1 the model matched the reference exactly (--check-model, 05.11.).
- **K02 Evaluation (in-sample)** (Confirmed; Design; → meio_seeker_stochastic.py §3, §5): Seeker evaluates a policy on its own N = Settings!NumScenarios (200) scenarios: demand per channel and week drawn from the quantile forecast with Settings!RandomSeed (K09), lead times as categorical distributions. Objective = aggregate_mean(total cost) = expected cost. Constraints: per channel and constrained week, share of scenarios with FR ≥ target ≥ chance level (H05–H07). Seeker 2.1 assigns the drawn demand values to its scenarios in its own order (measured 05.11.), so these scenarios exist only inside Seeker.
- **K03 Out-of-sample check** (Confirmed; User (18:42); → meio_seeker_stochastic.py §0, §6): After optimization the same model (§3) is built again with fresh random demand (seeds RandomSeed + 1, + 2, … per batch), the optimized decisions set as the variable values, and evaluated once — no search. Default OUT_OF_SAMPLE_SCENARIOS = 2,500 (can be increased), in batches of OUT_OF_SAMPLE_BATCH = 2,500 scenarios per Seeker model (lower it if memory runs short). Means and shares are combined exactly across batches; P10/P90 are batch averages. Precision of a 99% share with 2,500 scenarios: ±0.2 percentage points (one standard error). Guards against a plan that only works on Seeker's 200 scenarios.
- **K07 Start policy = warm start (one fixed policy)** (Confirmed; User (19:30); → meio_seeker_stochastic.py §0, §4): Seeker starts its search from one fixed (s,S) policy computed from the forecast (pure formula, no evaluation; also the baseline for the reported saving). Per week u: expected demand μ_u = Σ over channels of the mean of the 10 quantiles; standard deviation σ_u = √ Σ over channels ((Q95 − Q05)/3.29)² (normal approximation). cover(t, W) = Σ μ_u + z·√Σ σ_u² over weeks t … t+W−1 (cut at the horizon). lot = max(production MOQ 6,000, 4 × average weekly μ). FG1 at the DC: s_t = cover(t, max production LT + 1 + 2 = 9 weeks), S_t = s_t + lot. RM k (echelon): s_t = BOM_k × cover(t, max LT_k + max production LT + 1 + 4 weeks), S_t = s_t + max(MOQ_k, BOM_k × lot). Inactive tail weeks 0 (K04); values rounded to the decision steps (K11). Settings in §0: START_Z = 4, START_EXTRA_WEEKS_FG = 2, START_EXTRA_WEEKS_RM = 4, START_LOT_WEEKS = 4 — the combination that met all 90 constraints in the earlier calibration and on Seeker's scenarios (€119,981, 05.11.). A grid of start policies scored by Seeker was dropped: Seeker 2.1's set_value re-evaluates the whole model after every value (measured 05.11.), which makes scoring many start policies impractical.
- **K08 Optional safety margin** (Confirmed; Design; → meio_seeker_stochastic.py §0): OPTIMIZATION_CHANCE_LEVEL (e.g. 0.995) makes the optimization stricter than the business rule to protect out-of-sample performance; the report always checks against Settings!FillRateChanceLevel.
- **K09 Seeker stochastic environment** (Confirmed; User (21:10); → meio_seeker_stochastic.py §3): Demand per channel and week is a Seeker user distribution built from the 10 quantiles (G02). Seeker 2.1 has no oversampling for user distributions, so the distribution returns stratified draws (one per equal probability band, in random order); Seeker 2.2+ oversampling (maxSample = 5 × scenarios) is used automatically where available. Stochastic lead times are categorical distributions. About 13k Terms with fixed and 29k with stochastic lead times. Constraint form FILL_RATE_CONSTRAINT_FORM: 'frequency' (default) or 'quantile' (H07).
- **K10 Variable priorities** (Confirmed; User (22:55); → meio_seeker_stochastic.py §0, §3): Seeker's variable_priority makes it try to change high-priority variables more often (priorities are relative). FG1 5 (drives production and transport cost), RM3 Erdbeere 4 (supply bottleneck, perishable, largest raw-material cost), RM4 Ananas 2 (perishable, not binding), RM1 Große Dose 1 and RM2 Pappboden 1 (cheap, non-perishable, not binding). Same priority for s and S−s and for every week. Set via VARIABLE_PRIORITY in §0; applied right after the variables are created in build_model (§3).
- **K11 Decision step size** (Confirmed; Design (22:55); → meio_seeker_stochastic.py §0, §2): Decision step = batch / order multiple × STEP_FACTOR: FG1 100 cans, RM1/RM2 720 pcs, RM3 50 kg (5 × 10 kg), RM4 100 kg. Coarser strawberry steps cut that search dimension 5× with negligible effect on cost.
- **K12 Start policy always inside the bounds** (Confirmed; Design; → meio_seeker_stochastic.py §2, §8): After the rule bounds (K05) the upper bound of each reorder point is raised to at least ⌈1.25 × start s / step⌉ (START_BOUND_MARGIN) and, for FG, the upper bound of the gap to at least the start gap, so Seeker can start from the start policy and move above it. Raw-material gaps are not raised: a gap above the max order behaves exactly like the max order (tested: identical cost and fill rates in every scenario).
- **K13 Seeker stochastic settings (from your test runs)** (Confirmed; User runs 04.–05.11.; → meio_seeker_stochastic.py §0): STOCHASTIC_SPEED = 0: at 0.5 Seeker 2.1 accepted no move in 17,099 evaluations; at 0 it improves (~17–32 evaluations/s). FILL_RATE_CONSTRAINT_FORM = 'frequency': 4.7% saving in 180 s vs 2.0% with 'quantile'. Both forms accept the same plans. 250 s run (05.11.): Seeker 112,512 expected cost with all 90 constraints met in-sample; 113,142 and 88/90 on 10,000 fresh scenarios. Seeker 2.1 finishes about 15% after the time limit (288 s for 250 s).
- **K14 Reading results from Seeker** (Confirmed; User (08:31, 18:34); → meio_seeker_stochastic.py §0, §5–§6): After an evaluation the script reads only single numbers: aggregates (mean; P10/P50/P90 via aggregate_quantile; shares via aggregate_relative_frequency_geq) and Terms that are the same in every scenario (e.g. week-1 decisions). Measured on Seeker 2.1 (05.11.): 91 single numbers in 0.0 s, one full evaluation 2.9 s, but 0.5–2.9 s for each per-scenario value list — such lists are never read. Time limit: TIME_LIMIT_SECONDS in §0 (None = Excel SolverTimeLimit). If the results workbook is open in Excel, it is written to a time-stamped name instead. Every phase is timed (console and report Summary).
- **K15 Where the reported numbers come from** (Confirmed; User (18:42); → meio_seeker_stochastic.py §5–§7): In-sample = Seeker's 200 optimization scenarios: expected cost, cost parts, share of scenarios meeting each fill-rate target, start-policy cost and saving. Out-of-sample = the fresh scenarios of §6: expected cost and cost parts, mean fill rate and share meeting the target per channel and week, decision distributions per week (mean, P10, P90, probability of an order), median arrival week of commit-now orders, mean stock, waste and holding cost per week. Week-1 decisions are the same in every scenario (A04), so they are exact.
- **K16 Solver-free alternative: simulation-optimization (meio_simopt.py)** (Confirmed; User (20:33); → meio_simopt.py): Same data, rules A–J, decision variables, steps, bounds and outputs as the Seeker model, without Seeker. The model is one vectorized simulator (§3 of meio_simopt.py); it equals the independent reference implementation scenario by scenario (tested incl. uncertain lead times, lots arriving already too old, incremental tiers, zero demand, freshness limit), and that reference matched the Seeker model exactly on Seeker 2.1. Futures are drawn stratified from the forecast. Rule: per channel and week the share of futures meeting the target ≥ chance level (H05), judged as (v+1)-th smallest fill rate; cost only counts once every rule holds (penalty). Step A: coordinate search on the formula policy (per stock point: safety factor z, extra cover weeks, gap S − s, last order week; the FG gap starts just above the first production price tier, 15,100). Step B: local search on the 244 weekly variables (±1/±2 steps per variable, ±1 step per 4-week block, adaptive step sizes), each round judged on 1,000 futures = newest set of 500 + previous set (8 sets, cycling), so the plan cannot over-fit one set; result = last plan meeting every rule at the end of a round. Benchmark 05.11. on 10,000 fresh futures (Seeker: its own 2,500-future check): Seeker 250 s → €113,196, 88/90 rules; simopt 55 s → €112,892, 88/90; simopt 250 s → €109,066 (−3.6%), 88/90. - **K17 Feasibility check: weeks that fail whatever we decide** (Confirmed; User (06.11. 20:52); → meio_seeker_stochastic.py §0, §4b): Before the search, Seeker evaluates one extra policy on the optimization scenarios (same count and seed): maximum supply — in every active week a reorder point above any reachable inventory position, so every raw material orders its max order and FG produces its maximum (still limited by raw materials on hand, MOQ and batch; all rules of section 3 unchanged). A fill-rate rule 'fails whatever we decide' if neither this policy nor the start policy meets it at Settings!FillRateChanceLevel. Both are needed because no single policy is an upper bound: producing everything at once can leave later weeks without fresh stock. Tested on the 25 stress cases: start + maximum supply give the same verdict as 11 supply-rich policies on 1,500 NumPy futures — no false alarm where the rules are reachable, and it finds the strawberry gaps (e.g. demand +30%: weeks 11, 15–19; cancelled strawberry orders: weeks 15–16).
