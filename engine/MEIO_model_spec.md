# MEIO model (Seeker): specification of assumptions, mechanics & dynamics

The same list is in the Excel sheet *Model_Assumptions*. The implementation is `meio_seeker_stochastic.py` (v18.1): every rule below is written once, as Seeker Terms in its section 3. `reference_simulator.py` implements rules A–J a second time, independently, and `test_engine.py` requires both to agree in every scenario.
Status: **Confirmed** = decided by user · **Given** = user data · **Proposed** = default, to be confirmed.


## A. Time & planning

- **A01 Period** (Confirmed; User Q1; → Settings): One period = one calendar week. Period 1 starts on Settings!PlanningStartDate. All times (lead times, shelf lives) are whole periods.
- **A02 Planning horizon** (Confirmed; User Q1; → Settings): The model simulates and optimizes H = 36 periods (Settings!HorizonPeriods). Horizon rule (A05): the end-of-horizon effect reaches back about one echelon lead time (longest raw-material lead time + production lead time; template 12 + 6 = 18 weeks), so choose H ≥ that + R + a margin of several weeks; then the committed weeks 1..R lie well before it (template: 36 ≥ 18 + 2 + 16). Input warning X10 (K19) checks it with a margin of 8 weeks.
- **A03 Review period R and the planned position between runs** (Confirmed; User Q1/Q29; review period and planned position: User (12.11.); → Settings!ReviewPeriod; script §3, §4, §7): Settings!ReviewPeriod = R (default 1): the model is run in weeks 1, 1 + R, 1 + 2R, …; new data (stock, open orders, forecast) arrive and decisions are taken only at a run. Each run commits every decision of weeks 1..R as exact quantities; later weeks are indicative and re-planned at their run. Planned position: in a run week the (s,S) rules use the actual inventory position (C01, C03); in the weeks between runs they use the planned position = the position at the last run + the orders planned since − the expected demand since (forecast mean = mean of the 10 quantiles summed over the channels, as in K07; for raw material k on the echelon: BOM_k × that demand), never below 0 (lost sales; so s = 0 still means 'no order', C06). Like the actual position it is age-blind (K22). Orders inside a cycle therefore do not react to the demand that actually happens; the physics (receipts, FEFO, waste, lost sales) runs on the actual demand of every scenario, and a planned production order is still limited by the raw material on hand in its week (D02). An order can be planned for every week of the cycle, so weekly capacities are kept, and R = 1 is exactly the weekly model of v18 (regression test 12.11.). Literature: within a cycle the quantities are fixed at the run ('static uncertainty', Bookbinder & Tan 1988, Management Science), across cycles they are re-planned (receding horizon, Dural-Selcuk, Rossi, Kilic & Tarim 2020, Omega); the planned position is the 'reference inventory position' (latest observed position + orders placed since) of inventory problems with periodic information delays, for which (s,S) levels that depend on the age of the information are optimal (Bensoussan, Çakanyıldırım & Sethi 2006, JOTA; 2007, POMS) — subtracting the expected demand only shifts those levels, which are free per week here. Not taken: orders only in run weeks (one order per cycle, an (R,s,S) policy), which would cut weekly capacities such as RM3's 1,000 kg per order to one order per cycle.
- **A04 Event sequence within a period t** (⚠️ Proposed; Proposed (changed: review before demand); → Math model §3): E1) Receipts due in t arrive with full shelf life. E2) FG review at DC → production order (D02); its raw materials leave RMW the same week (B02). E3) RM review at RMW on echelon stock → supplier orders (D01). E4) Customer demand of t is served from DC stock (H02/H03). E5) Holding cost on end-of-week on-hand. E6) Ageing −1 week; lots no longer usable are scrapped immediately (F05). Reviews happen at the START of the week (before demand), so the decisions of weeks 1..R depend only on today's known stock and the forecast and are exact (A03).
- **A05 No terminal valuation (end-of-horizon effect)** (Confirmed; User (06.11. 20:48); measured and reading rules: User (12.11.); → Settings!TerminalInventoryValue): Inventory left after the last week H has no value (and no cost beyond its holding up to H): the model plans as if the business stopped after week H. Consequence, measured 12.11. (template, target 95%): the cheapest plan runs stock down towards the end. A NumPy search with rule E reached €94.7k against Seeker's €112.7k at almost the same service (lost demand 0.5% vs. 0.1%), nearly all of it by leaving less stock after week 36 (FG 2,436 vs. 4,339; RM1 655 vs. 7,191; RM2 320 vs. 6,366): €14.4k less spent on orders placed in weeks 13–30. In reality week H + 1 follows, so this is not a real saving. Kept deliberately (User 12.11., lean): decisions are committed only for weeks 1..R and the model is re-run every R weeks (A03), so the end moves forward and never reaches the committed weeks, provided the horizon is long enough (A02); in the 12.11. comparison both plans had the same week-1 decisions. How to read results: (1) act only on the commit-now decisions of weeks 1..R; (2) later weeks are indicative, and the last weeks (about one echelon lead time before H, template: from week 19) show a business winding down: low stock, fewer orders, the weakest fill-rate cells (e.g. AMZ week 36); (3) total cost and 'Saving vs. start policy' are spending within weeks 1..H, partly from running stock down, so compare costs only between runs with the same horizon and data; (4) part of Seeker's search may go into this run-down. Alternatives not taken: an end-stock credit at purchase cost, or an end-stock target (position in week H ≥ the start policy's safety stock).

## B. Network & material flow

- **B01 Network** (Given; User; → Locations, Items, Sourcing): Suppliers (Erdbeerhof Köln: RM3; Verpackungslieferant: RM1, RM2; Ananas CR: RM4) → raw material warehouse RMW → production site KAJA → distribution center DC → channels AMZ, D2C, B2B. One finished good FG1, four raw materials.
- **B02 RMW → KAJA transfer (derived decision)** (Confirmed; User Q5/Q8; → Lanes L_RMW_KAJA, BOM): Not optimized separately. In the week a production order of q units is placed, BOM_k × q of each raw material k is withdrawn from RMW (FEFO, F04) and shipped to KAJA. The transfer time is contained in the production lead time.
- **B03 KAJA holds no inventory** (Given; User; → Locations KAJA): Raw materials are consumed on arrival; finished goods are shipped to the DC on completion. There is no stock at KAJA in the model, only the production pipeline.
- **B04 DC → channels** (Confirmed; User Q15; → Lanes, LeadTimeDist LT_ZERO): Channels are served directly from the DC with zero transit time (instant serve).
- **B05 Storage capacity** (Confirmed; User Q22; → Locations): No storage capacity limits at RMW or DC.

## C. Inventory policy (s,S)

- **C01 FG1 policy at DC** (Confirmed; User Q2; → Settings!FGInventoryPositionBasis): Dynamic (s_t, S_t) per week t for FG1. Inventory position IP_FG(t) at the start-of-week review = DC on-hand still sellable this week (remaining shelf life ≥ 16) + all open production orders (FG pipeline). Lost sales → no backorders in IP. If IP_FG(t) < s_t (C06), a production order of S_t − IP_FG(t) is triggered and rounded/limited per D02. Not shelf-life aware (K22): the position counts every lot still sellable this week in full, also stock that will expire unsold before a production order placed now reaches the DC, and lots that only less demanding channels may take (template: lots with 16–23 weeks left are D2C only). Between runs the rule uses the planned position (A03).
- **C02 Unsellable FG is wasted immediately** (Confirmed; User (19:49); → Math model E2/E6): FG lots that no channel can use any more are scrapped immediately (waste cost) and never count in IP_FG. A lot with exactly 16 weeks left still counts at the start-of-week review and can serve this week's D2C demand; whatever is left of it at week end is scrapped.
- **C03 RM policy at RMW (echelon)** (Confirmed; User Q2/Q4; → Settings!RMInventoryPositionBasis): Dynamic (s_kt, S_kt) per raw material k and week t, in RM units. Echelon inventory position IP_k(t) = usable RMW on-hand of k + open supplier orders of k + BOM_k × IP_FG(t) (raw material embedded in downstream FG stock and production pipeline). The RM review happens after the FG review in the same week, so a production order itself does not change the echelon position. Only RM lots still usable next week count (C04). If IP_k(t) < s_kt (C06), order S_kt − IP_k(t), rounded/limited per D01. Not shelf-life aware (K22): the echelon position counts (a) BOM_k × FG stock that will expire unsold before a raw-material order placed now can become FG, and (b) usable raw material that will expire before production uses it; it does not check that the raw material on hand covers one production lot (BOM_k × MOQ) — the start policy's lot guard (K07) covers that at the start. Between runs the rule uses the planned echelon position (A03).
- **C04 Unusable RM is wasted immediately** (Confirmed; User (19:49), by analogy; → Math model E3/E6): Same rule as C02 for perishable raw materials: RM3/RM4 lots that can no longer be used in production are scrapped immediately. In IP_k only lots with remaining shelf life ≥ 37 at the RM review count (still usable, ≥ 36, at next week's production). Non-perishables (RM1, RM2) count fully.
- **C05 Weekly variable s,S** (Confirmed; User Q3; → Settings!PolicyBlockLength): s and S may take a different value in every week of the horizon (block length 1). Encoding: s_t ≥ 0 and gap Δ_t = S_t − s_t ≥ 0, so that S_t ≥ s_t holds by construction.
- **C06 Strict order trigger** (Confirmed; Design; → Math model E2/E3): An order is triggered when IP < s (strictly), and the quantity is S − IP > 0 before rounding. s = 0 therefore means 'never order this week' (also between runs: the planned position is never below 0, A03). This avoids MOQ-inflated orders when IP = s = S.

## D. Order & production rules

- **D01 Raw material order quantity** (Confirmed; User Q20; → Sourcing): q = S − IP → round UP to OrderMultiple → if q < MOQ then q = MOQ → if q > EffectiveMaxOrderQty then q = EffectiveMaxOrderQty (MaxOrderQty rounded down to a multiple of OrderMultiple: RM1 19,440, RM2 39,600, RM3 1,000 kg, RM4 10,000 kg). At most 1 order per raw material per week; the max applies per order.
- **D02 Production order quantity** (Confirmed; User Q9; → Production, BOM): q = S − IP → round UP to BatchSize (100) → raise to MOQ (6,000) → cap at MaxQtyPerOrder (50,000) → cap by raw material availability: for each component k, q ≤ usable RMW stock of k / BOM_k → round DOWN to BatchSize. If the result is < MOQ, nothing is produced this week.
- **D03 One production line** (Confirmed; User Q7; → Production!MaxOrdersPerPeriod): At most one production order can be started per week, and orders complete in the sequence they were started (an order started later can never arrive at the DC earlier).
- **D04 Concurrent production orders** (Confirmed; User (20:00), option 1; → Production): Several production orders can be in the pipeline at the same time (one start per week, each taking the production lead time); with no overtaking (E04) they arrive in start order.
- **D05 Rounding direction** (⚠️ Proposed; Proposed; → —): Policy quantities are rounded UP to the batch multiple (to reach the order-up-to level). Availability caps are rounded DOWN (you cannot produce from material you don't have).

## E. Lead times

- **E01 Supplier lead time** (Confirmed; User Q7; → Sourcing, LeadTimeDist): Time from order placement in week t to arrival at RMW at the start of week t + L. Current data: fixed RM1 4, RM2 4, RM3 8, RM4 12 weeks.
- **E02 Production lead time** (Confirmed; User Q5/Q6; → Production, LeadTimeDist): Time from production order in week t (raw materials leave RMW the same week) to arrival at the DC at the start of week t + L. Includes the RMW→KAJA transfer, production and KAJA→DC transport. Current data: fixed 6 weeks.
- **E03 Stochastic lead times (switchable)** (Confirmed; User Q7; → LeadTimeDist): Each lead time is a discrete distribution (LeadTimeDist). The example uses fixed distributions; stochastic variants exist as *_STOCH IDs (RM1/RM2 4|6, RM3 8|12, RM4 12|16, production 6|8). Switch by changing LeadTimeDistID in Sourcing / Production. A lead time is drawn independently per order and scenario.
- **E04 No order crossing** (Confirmed; User Q21/Q7; → Settings!LeadTimeCrossing): Orders from the same source never overtake each other: arrival(order n) = max(t_n + L_n, arrival(order n−1)). Applies to each raw material's supplier stream and to the production line.

## F. Shelf life, FEFO & waste

- **F01 Shelf life starts at arrival** (Confirmed; User Q2/Q10; → Items): The shelf-life clock of a lot starts when it arrives at its stocking location: raw materials at RMW, FG1 at the DC. Time at the supplier, in transit or in production does not consume shelf life. Each lot arrives with full shelf life.
- **F02 Shelf lives** (⚠️ Proposed; User + change; → Items!ShelfLife): FG1 36 weeks from DC arrival. RM3 Erdbeere and RM4 Ananas 52 weeks from RMW arrival (raised from 44, as you allowed, to lengthen the usable window). RM1 Große Dose and RM2 Pappboden do not expire.
- **F03 Freshness rule at production** (Confirmed; User Q11; → BOM!MinRemainingShelfLife): RM3/RM4 can be withdrawn for production only if their remaining shelf life is ≥ 36 weeks in the production-order week. Usable window after arrival = 52 − 36 = 16 weeks.
- **F04 FEFO issuing** (Confirmed; User Q13; → Settings!IssuingRule): At RMW and DC, lots are issued first-expired-first-out among the lots eligible for the use (production, or a specific channel).
- **F05 Waste** (Confirmed; User Q14/Q26; → Costs!WasteCost): A lot is scrapped at the end of the week in which it becomes unusable for every purpose: RM3/RM4 when remaining shelf life < 36; FG1 when remaining shelf life < 16 (the lowest channel requirement). Waste cost = scrap cost per unit only (material value is sunk).
- **F06 Stock in its last usable week (end stock and waste)** (Confirmed; User (08.11. 12:35); → Math model E5/E6): A lot counts as stock in every week in which it can still be used: in the stock position, for sales (to the channels whose freshness need it meets) or for production, in that week's end stock and in its holding cost. In its last usable week (FG1: exactly 16 weeks left; RM3/RM4: exactly 36 weeks left at production) whatever is left at week end is scrapped and booked as waste of that same week; from the next week on it appears nowhere. So the end stock of week t is the stock after demand, before the end-of-week scrapping, and per scenario: end stock(t) = end stock(t−1) − waste(t−1) + receipts(t) − sales(t) (raw materials: − transfers to production instead of sales). This balance, and sales + lost sales = demand, are checked per scenario and week in test_engine.py.

## G. Demand & scenarios

- **G01 Probabilistic forecast input** (Confirmed; User; → Demand): Per channel and week: 10 quantiles at probability levels 0.05, 0.15, …, 0.95 (each quantile = centre of a 10% probability band), as produced by a probabilistic forecaster. The format describes each cell on its own; it holds no information on how channels and weeks move together (G02).
- **G02 Scenario sampling** (⚠️ Proposed; User Q19 + proposed tails; independence: User (12.11.); → Settings!DemandSampling): Per scenario, channel and week: draw u ~ Uniform(0,1) and read demand from the piecewise-linear quantile function through the 10 points. Tails: from u = 0 at max(0, Q05 − (Q15 − Q05)/2) to Q05; from Q95 to Q95 + (Q95 − Q85)/2 at u = 1. Rounded to whole units. Futures are drawn INDEPENDENTLY: every channel and every week gets its own u, so the futures carry no correlation — neither from week to week (a strong week 5 says nothing about week 6) nor across channels (no common trend for D2C, B2B and Amazon). Every result of the engine (expected cost, fill rates, P10 and worst-5% figures, waste, the start formula K07) holds under this assumption. If real forecast errors persist over weeks or move together across channels, totals over several weeks vary more than the engine assumes, and its fill rates are too optimistic (template, 9-week FG cover window: spread 1,793 units when independent, 2,240 at a week-to-week correlation of 0.3, 2,971 at 0.6). The quantiles of each cell would stay the same; only how the cells combine into futures changes. Open, noted for the forecasting tool (User 12.11.): check from past forecast errors whether they are correlated; if so, either the forecaster delivers simulated demand paths, or the engine gets a correlation setting.
- **G03 Example forecast character** (⚠️ Proposed; Generated; → Demand!Event): Generated data: seasonal baseline with spiky week-to-week noise, promotion weeks (AMZ w9, w10, w27; D2C w14, w30; B2B w18, w33) with 2.2–3.8× mean and wide uncertainty, flat weeks (AMZ w20–22; D2C w5–7; B2B w24–25) with a stable level and very narrow uncertainty. Average about 1,400 units a week in total.
- **G04 Unmet demand** (Confirmed; User Q17, User (06.11. 20:48); → Channels!UnmetDemand): Demand not served in its week is lost (all channels). No backorders. Lost sales have no cost: they are limited only by the fill-rate rules (H05). Consequence: a plan that misses rules sells less and therefore looks cheaper, so costs are only compared between plans that meet the same rules.

## H. Channel allocation & fill rate

- **H01 Channel eligibility** (Confirmed; User Q15; → Channels!MinRemainingShelfLife): A unit can be shipped to channel c only if its remaining shelf life ≥ requirement_c: AMZ 24, D2C 16, B2B 24 weeks. FG1 is therefore sellable to AMZ/B2B for 12 weeks after DC arrival and to D2C for 20 weeks.
- **H02 Shortage allocation (serving order)** (Confirmed; User Q16; priority as input: User (12.11.); → Channels!ShortagePriority): Channels are served one after another in the order of Channels!ShortagePriority (input since 12.11.; 1 = served first, each rank once): template D2C 1 → B2B 2 → AMZ 3, the same order as before, when it was derived from the channel targets. Each channel takes as much as it can of its demand before the next is served.
- **H03 Lot selection per channel** (⚠️ Proposed; Proposed (FEFO + H01); → —): Within its turn, a channel takes FEFO from the lots eligible for it. As a result D2C consumes the older 16–23-week lots that AMZ/B2B cannot take anyway, before touching fresher stock.
- **H04 Fill-rate definition: one target per product, measured per cell** (Confirmed; User Q18; one target per product: User (12.11.); → Items!TargetFillRate; Settings!FillRateDefinition): One fill-rate target per product: Items!TargetFillRate (finished goods only), the same for every channel (User 12.11.: fewer inputs and knobs; Channels!TargetFillRate was removed). FR(c, t, scenario) = units served to channel c in week t ÷ demand of c in week t; FR = 1 if demand = 0. Measured per channel and per week (a 'cell') and per scenario; never pooled over weeks or channels, so good weeks cannot average away a bad week.
- **H05 Fill-rate rule: expected fill rate of every cell ≥ target** (Confirmed; User Q18; rule E: User (12.11.); → Items!TargetFillRate; script §3): For every channel c and every constrained week t (H06): expected fill rate = mean over the scenarios of FR(c, t) ≥ the product's target. There is no separate chance level (Settings!FillRateChanceLevel removed, User 12.11.): how often and how badly a week is short is inside the one number. Example (target 95%, 100 scenarios, AMZ week 12): 94 scenarios fully served, 3 at 80%, 3 at 0% → (94 × 100% + 3 × 80% + 3 × 0%) ÷ 100 = 96.4% ≥ 95% → met: on average Amazon gets 96.4% of its week-12 demand. Why it replaced the chance rule (share of scenarios with FR ≥ target ≥ 99%): a short week is nearly always empty (most misses had a fill rate near 0), so lowering the target saved nothing; re-optimized with NumPy (60 s, 2,000 fresh scenarios): chance rule at targets 98 / 95 / 90% → €107.6k / €108.3k / €107.1k, this rule → €107.6k / €105.5k / €99.6k. The mean is estimated from the scenarios: standard error ≈ √(p(1 − p) ÷ N) for all-or-nothing weeks, e.g. ±2.2 points at 95% with N = 100 and ±1.5 with N = 200; the fresh-scenario check (K03) shows how well it holds.
- **H06 Constrained weeks** (⚠️ Proposed; Proposed; → Settings!FillRateEnforcementStart): Constraints apply from the first week that any new decision can influence, i.e. week 1 + production lead time (= week 7 with fixed 6 weeks). Earlier weeks are fully determined by the initial state and open orders; they are reported but not constrained (otherwise the model could be infeasible whatever it decides).
- **H07 Fill-rate rule in Seeker** (⚠️ Proposed; Design (12.11.); → Math model C1; script §3): FILL_RATE_CONSTRAINT_FORM = 'mean' (default): per constrained cell enforce_geq(aggregate_mean(FR(c, t)), target); 'none' switches the rules off (diagnostic only). The chance-level forms 'frequency' and 'quantile' were removed with H05 (12.11.). Same number of Seeker Terms as before (one aggregate per cell).

## I. Costs & objective

- **I01 Objective** (Confirmed; User Q27; → —): Minimize expected total cost over the horizon (average over scenarios) = RM ordering + production + transport + holding + waste, subject to the fill-rate rules (H05). No shortage penalty. No value for stock left after week H (A05).
- **I02 Raw material ordering** (Confirmed; User Q25; → Costs): Per order: fixed cost per raw material order line + variable cost per unit ordered. Each raw material is its own order line, with no shared fixed cost per supplier delivery.
- **I03 Production** (Confirmed; User Q24; → Costs, CostTiers): Per production order: fixed cost + variable unit cost from tier table CT_FG1_PROD, all-units pricing on the order quantity (the whole order is priced at the tier its quantity falls into).
- **I04 Transport** (Confirmed; User Q24; → Lanes, CostTiers): KAJA→DC transport is priced per production order quantity with tier table CT_FG1_TRANSPORT (all-units). RMW→KAJA transfers and DC→channel shipments are free.
- **I05 Holding** (Confirmed; User Q23; → Costs!HoldingCost): Holding cost per unit per week on end-of-week on-hand at RMW (raw materials) and DC (FG1). No holding cost on pipeline or in-transit stock.
- **I06 Waste** (Confirmed; User Q26; → Costs!WasteCost): Scrap cost per unit for every scrapped lot (F05).
- **I07 Cost timing & scope** (⚠️ Proposed; User Q23/Q26 + design; → Math model §4): Ordering, production and transport costs are counted in the week the order is placed, for all orders placed in weeks 1..H (also those arriving after H). Orders already open at the start are sunk and not counted. Holding is charged on end-of-week on-hand, including lots scrapped at the end of that week. Raw material purchase cost of later-wasted material is part of ordering cost; waste adds only the scrap cost.

## J. Initial state

- **J01 On-hand at start** (Confirmed; User Q28; → Init_Inventory): Init_Inventory lists on-hand stock at the start of week 1 per location × item × remaining shelf life lot.
- **J02 Open orders** (Confirmed; User Q28; → Open_Orders): Open_Orders lists released but not yet arrived supplier orders (Purchase) and production orders (Production) with their arrival week. Open production orders already consumed their raw materials. Lots arrive with full shelf life (F01) unless RemainingShelfLifeAtArrival is given.
- **J03 Open orders in policy positions** (⚠️ Proposed; Proposed (follows C01/C03); → —): Open production orders count in IP_FG; open supplier orders count in IP_k; both count in the echelon position via C03.
- **J04 Lots already unusable when they enter (known limitation)** (Confirmed; User (08.11. 12:35); → Init_Inventory, Open_Orders): Initial stock or an open order entered with a remaining shelf life below the lowest channel need (FG1: 16 weeks) or below the production freshness rule (RM3/RM4: 36 weeks) is never sold or used and never counts in a stock position, but it appears for one week in that week's end stock and holding cost before it is scrapped at week end (strictly it should be scrapped on arrival). Not handled because it does not occur in practice; the template has no such lot (lowest FG lot 19 weeks, lowest raw-material lot 38 weeks). The current behaviour is pinned by a test.

## K. Optimization (Seeker)

- **K01 Decision variables** (Confirmed; Design; → meio_seeker_stochastic.py §2): Per stock point j (FG1 at DC; RM1–RM4 at RMW) and active week t: σ_jt, δ_jt ∈ {0, 1, …, upper bound} integers; s_jt = m_j·σ_jt and S_jt = s_jt + m_j·δ_jt, with decision step m_j (K11). 244 variables with the current data (K04).
- **K04 Inactive tail weeks fixed to s = S = 0** (Confirmed; Design; → meio_seeker_stochastic.py §2): With no terminal value, an order that cannot arrive within the horizon is pure cost. So FG s,S are only free for t ≤ H − min production LT (= 30), and RM k only for t ≤ H − min production LT − min LT_k (RM1/RM2 26, RM3 22, RM4 18). Later weeks are fixed to 0, which shrinks the search from 360 to 244 variables.
- **K05 Variable bounds (lower 0, upper from the forecast)** (Confirmed; User (22:55, 19:40); → meio_seeker_stochastic.py §0, §2): Lower bound 0 for every variable (s = 0 means 'do not order this week'). Upper bounds, with Q95 = sum of the weekly 95% quantile of total demand over a window of weeks (cut at the horizon): reorder point s of FG ≤ Q95 over (max production LT + 1 + EXTRA_COVER_WEEKS['FG']) weeks; reorder point s of RM k ≤ BOM_k × Q95 over (max LT_k + max production LT + 1 + EXTRA_COVER_WEEKS[k]) weeks; FG gap S − s ≤ min(max production qty; max(MOQ; Q95 over the 20 sellable weeks after arrival)); RM gap S − s ≤ max order qty (a larger gap behaves exactly like 'order the maximum'), perishable RM additionally ≤ max(MOQ; BOM × Q95 over the 16 usable weeks after arrival). Bounds are rounded up to the decision step (K11) and raised if needed to contain the start policy (K12). EXTRA_COVER_WEEKS per stock point in §0: FG 8, RM1 4, RM2 4, RM3 8, RM4 4 — RM3 raised from 4 to 8 because its week-12 reorder point sat at the bound in the 05.11. runs (week-12 bound 23,300 → 27,550 kg); FG raised from 4 to 8 because its week-13 reorder point sat at the bound in two 250 s runs (05.11., 06.11.; week-13 bound 25,300 → 35,500 cans). If a run reports a reorder point at its upper bound (console NOTE and Summary row, naming the setting), raise that stock point's EXTRA_COVER_WEEKS. Search space about 10^480.
- **K06 One model, written once in Seeker** (Confirmed; User (18:42); → meio_seeker_stochastic.py §3): Every rule of sections A–J (lots and shelf life, FEFO, channel priority, (s,S) ordering with MOQ/batch/max, echelon positions, lead times without overtaking, waste, costs, fill rates) is written exactly once: as Seeker Terms in section 3 of the script, in Seeker's stochastic environment. No other code computes supply-chain dynamics; every reported number comes from Seeker evaluating this one model (optimization §5, out-of-sample check §6). Python only reads data, sets variable bounds, computes the start-policy formula (§4) and formats the report. Retired: the sampling version meio_seeker.py (NumPy simulator inside Seeker) and the NumPy replay of v7–v9. Correctness is checked outside the script: an automated test suite compares the Seeker model scenario by scenario with an independent reference implementation (cost, cost parts, fill rates, orders, arrivals, stock, waste, holding) and is itself mutation-tested; on real Seeker 2.1 the model matched the reference exactly (--check-model, 05.11.).
- **K02 Evaluation (in-sample)** (Confirmed; Design; → meio_seeker_stochastic.py §3, §5): Seeker evaluates a policy on its own N = Settings!NumScenarios (200) scenarios: demand per channel and week drawn independently from the quantile forecast (G02) with Settings!RandomSeed (K09), lead times as categorical distributions. Objective = aggregate_mean(total cost) = expected cost. Constraints: per channel and constrained week, expected fill rate ≥ target (H05–H07). Seeker 2.1 assigns the drawn demand values to its scenarios in its own order (measured 05.11.), so these scenarios exist only inside Seeker.

- **K07 Start policy = warm start (one fixed policy)** (⚠️ Proposed; User (19:30), revised 10.11.; → meio_seeker_stochastic.py §0, §4): Seeker starts its search from one fixed (s,S) policy computed from the forecast (pure formula, no evaluation; also the baseline for the reported saving). It sits in section 4 of the script; section 5 evaluates it on Seeker's scenarios (start check). Target-aware safety factor (12.11.): z₀ = G⁻¹((1 − β) × μ ÷ σ_W) with the standard normal loss function G(z) = φ(z) − z(1 − Φ(z)), β = fill-rate target, μ = average weekly demand, W = FG cover window (max production LT + 1 + 2 weeks), σ_W = √(W × average weekly variance): the expected shortage before the next lot is ≈ σ_W·G(z) and falls in the last week, so that week's expected fill rate is ≈ 1 − σ_W·G(z) ÷ μ; clipped to [0, 4]. The formula ignores lots, freshness and lost sales, so if the start misses cells that maximum supply meets, the start check raises z to the next multiples of 0.5 (START_Z_STEP; a fixed grid, so a lower target never ends on a higher z) up to 4 (START_Z_MAX), each step one Seeker evaluation (17–25 s with 200 scenarios, 30–40 s with 500 on the user's PC, 12.11.), and keeps the first start that misses nothing; only then does the repair (K21) take over. START_Z = a number fixes z (no steps). Raw materials use the same z. Per week u: expected demand μ_u = Σ over channels of the mean of the 10 quantiles; standard deviation σ_u = √ Σ over channels ((Q95 − Q05)/3.29)² (normal approximation; adding variances, not quantiles, assumes independent channels and weeks as in G02). cover(t, W) = Σ μ_u over weeks t … t+W−1 + z·√Σ σ_u² over weeks r(t) … t+W−1 (cut at the horizon; r(t) = the run week that plans week t, A03: the safety stock also covers the demand since the last run, which the planned position only knows as its expectation; R = 1: r(t) = t). lot = max(production MOQ, min(4 × average weekly μ, what one fresh lot can sell before it expires = Σ over channels average weekly demand × (FG shelf life − channel need + 1))). FG1 at the DC: s_t = cover(t, max production LT + 1 + 2 weeks), S_t = s_t + lot. RM k (echelon): s_t = max(BOM_k × cover(t, max LT_k + max production LT + 1 + 4 weeks), BOM_k × (FG s_t + production MOQ)) — the lot guard: when FG falls to its reorder point and needs a lot, raw material for at least one MOQ is on hand or on order (without it production was blocked in the fast-moving test while the echelon position looked covered, C03); S_t = s_t + max(MOQ_k, BOM_k × lot). Inactive tail weeks 0 (K04); values rounded to the decision steps (K11). Settings in §0: START_Z = None (target-aware), START_EXTRA_WEEKS_FG = 2, START_EXTRA_WEEKS_RM = 4, START_LOT_WEEKS = 4. Tested 10.11. (NumPy, start policy, 2,000 fresh scenarios): template 89/90 → 90/90 rules met (the guard raises 4 raw-material reorder points in the last weeks, start cost €120.2k → €122.3k, so the template start and the saving baseline differ from v17.1); fast-moving data MOQ 6,000 60/69 → 66/69, MOQ 2,000 66/69 → 69/69. The lot cap did not bind in any tested case (MOQ or 4 weeks was smaller). A grid of start policies scored by Seeker was dropped: Seeker 2.1's set_value re-evaluates the whole model after every value (measured 05.11.), which makes scoring many start policies impractical.

- **K22 Inventory positions are not shelf-life aware (decision)** (Confirmed; User (10.11. 20:56); → MEIO_shelf_life_aware_policies.md): The (s,S) rules compare s with age-blind positions (C01, C03): every usable lot counts in full, also stock that will expire unsold (C01, C03 list exactly what is not subtracted).
